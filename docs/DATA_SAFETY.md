# Data Safety — Play Store Declaration Notes

Precise, current-state reference for filling out Play Console's Data Safety form. Every claim
below is verified against the actual code path as of Phase 3A, not aspirational. If a future
change alters any of this, update this file in the same commit — a stale Data Safety claim is a
Play Store policy violation, not just a documentation error.

## What MeetingMind actually does with data

**Recording audio, transcripts, and AI-generated content (summaries, decisions, action items,
questions) are processed and stored entirely on-device.** No recording, transcript, or AI output
is ever uploaded to any server, including Anthropic's, Google's, or Firebase's — see
`docs/AI_ARCHITECTURE.md` for the local inference architecture (VAD, ASR, diarization, and the
local LLM all run on-device via sherpa-onnx and MediaPipe).

Data collected/processed:

| Data | Collected? | Shared off-device? | Where it lives |
|---|---|---|---|
| Audio recordings | Yes (created by the app) | No | `context.filesDir/meetings/<id>/` — app-private storage |
| Transcripts, summaries, decisions, action items, questions | Yes (generated by the app) | No | Room database, app-private storage |
| Model files (ASR/diarization/LLM weights) | Downloaded by the app, on user request | Downloaded *from* Hugging Face / GitHub Releases over HTTPS — never uploaded | App-private storage |
| Account info (name, email) | Only if the user chooses to sign in with Google | Yes — to Firebase Authentication, for sign-in only | Not stored by MeetingMind beyond the session; managed by Firebase |
| Lightweight meeting metadata (title, date, duration, participant count, source type — never audio or transcript text) | Would be synced to Firestore if cloud sync were enabled | N/A in this build | `FirestoreSyncManager.syncMeetingMetadata()` exists in code but is **not wired to any UI** in this build — unreachable, dead code. Nothing is actually synced. |

## Sign-in (optional)

Google Sign-In via Firebase Authentication is available from Settings, never required. Onboarding
and all recording/transcription/AI functionality work fully without signing in. Signing in
transmits standard Google account identifiers (name, email, profile photo URL) to Firebase for
authentication purposes only — never meeting content.

## Network access

The app requests `INTERNET` permission for exactly two purposes, both explicit and user-initiated:

1. Downloading AI model files the user chose to install (AI Engine screen).
2. Firebase Authentication, only if the user chooses to sign in.

No background network calls occur as part of recording, transcription, diarization, summarization,
or Ask-Meeting — those are 100% local inference with no network dependency.

## Permissions and why each is needed

| Permission | Why |
|---|---|
| `RECORD_AUDIO` | Core recording functionality |
| `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MICROPHONE` | Keeps recording alive when the app is backgrounded/screen-locked |
| `FOREGROUND_SERVICE_MEDIA_PLAYBACK` | Global playback service (Media3 `MediaSessionService`) for the mini-player/lock-screen controls |
| `FOREGROUND_SERVICE_DATA_SYNC` | Required on Android 14+ for the WorkManager-backed background AI processing job (`MeetingProcessingWorker`) |
| `POST_NOTIFICATIONS` | Recording/playback/processing status notifications |
| `WAKE_LOCK` | Prevents the CPU from sleeping mid-recording |
| `INTERNET` | Model downloads and optional sign-in only (see above) — never for AI inference |

**No broad storage permission is requested.** Importing audio/video uses the system document
picker (`ActivityResultContracts.GetContent`), which needs no storage permission on any supported
API level.

## Android Auto Backup / device transfer

Recordings (`filesDir/meetings/`) and the Room database (`meetmind_database`, containing
transcripts/summaries/decisions/action items) are explicitly excluded from Android's Auto Backup
and device-transfer via `res/xml/data_extraction_rules.xml` / `res/xml/backup_rules.xml` — they
never leave the device through that mechanism either, consistent with the local-first claim above.

## Accurate claims for the Data Safety form

Use language like: *"Meeting recordings and transcripts are processed and stored locally on your
device. AI models are downloaded over HTTPS at your request but audio and transcripts are never
uploaded. If you choose to sign in, your Google account name and email are shared with Firebase
Authentication for sign-in only."*

Do **not** claim "no data is ever transmitted" — that would be false given optional sign-in and
model downloads, even though neither transmits meeting content.

## Known follow-up

`FirestoreSyncManager` is currently dead code (correctly scoped to metadata-only, but unreachable
from any UI). Either wire it up behind an explicit, clearly-labeled opt-in toggle in Settings, or
remove it, before shipping a build where the Data Safety form claims anything about cloud sync.
Until then, this file's "not wired to any UI" note must stay accurate.
