## Built

Numbers follow the brief's W9 items.

1. **`segment_signals`** in schema 19 (`core/database/Signals.kt`, `MIGRATION_18_19`).
   - Columns: `id`, `segmentId`, `meetingId`, `kind`, `entityId`, `value`, `confidence`, plus two of mine, `text` and `signalId`.
   - `signalId` groups the rows of one signal that cites several paragraphs, and `text` holds the signal's own words.
   - Indices on `meetingId`, `(meetingId, kind)` and `segmentId`.
2. **Extraction.**
   - `MeetingIntelligenceJsonParser` reads an optional `signals` array. Each signal needs a known `ItemKind`, some text and at least one real segment id. One that cites nothing the model was shown is dropped.
   - Commitments carry their `counterparty` and `due` as a small JSON object in `value`. The speaker becomes `entityId`. A decision only proposed carries `value = "PROPOSED"`. A `DEADLINE`'s `value` is the date.
   - Output in the older format (no `signals`) still parses with an empty list, and there is a test for that.
   - `RealMeetingIntelligenceEngine` and `GeminiIntelligenceEngine` ask for signals. `core/work/SignalKinds.kt` decides which kinds per `RecordingType`:
     - The base four (`COMMITMENT`, `DECISION`, `QUESTION`, `DEADLINE`) for work recordings.
     - Client calls, meetings and briefs get the wider set.
     - A standup gets blockers as `RISK` and `DEPENDENCY`.
     - `CONSULTATION` gets the base four only, and its prompt keeps "never add a diagnosis, dose or legal opinion that wasn't said".
     - Recordings that aren't work ask for none.
   - A model that offers other kinds isn't trusted with them: they're filtered out.
   - `WorkProfile.defaultSignalKinds()` gives what a profile shows by default: the base four, plus `RISK` and `REQUIREMENT` for Client work, Product and Legal.
   - `MeetingSummary.signals` is new (defaulted). The pipeline stores one `segment_signals` row per cited paragraph, and clears them when a recording is processed again.
3. **Change detection**, `core/work/Changes.kt` (`ChangeDetector`).
   - A cheap lexical and date match runs first. It compares new `DECISION`, `DEADLINE` and `SCOPE_CHANGE` signals against the project's open or active decisions, deadlines and scope items. The organisation stands in when the recording has no project.
   - It finds three reasons: a moved date, a reversal, or a replacement. The closest match wins.
   - A model then looks only at the candidates that survive. A firm date move needs no second opinion. An unreadable answer, or no model, leaves the proposal standing.
   - The verdict is cached per detector, so editing the Wrap-up doesn't ask again.
   - The output is a proposal only.
   - **Privacy:** `DeviceChangeModels` picks the model.
     - Anything `WorkPrivacy.mustStayOnDevice` covers only ever gets the local model, and the cloud transport isn't even asked whether it's configured.
     - Offline mode never asks the cloud either.
     - The check prompt starts with `TranscriptToolPrompts.FIDELITY_CONTRACT`.
   - `apply()` on confirm reuses the decision the Wrap-up already promoted from the same recording, so there's no duplicate. Otherwise it makes the item with its evidence. The new `ItemRepository.supersedeWith` sets the status and the link and logs the event.
4. **The Wrap-up.**
   - **Changes card:** "This replaces: Launch on October 14?" with the new words, ▶ at the moment, and Confirm / Not the same. Confirm shows "✓ Confirmed · Undo". "Not the same" is remembered on the phone.
   - **Tasks split:** the sections now read **You owe** and **They owe**.
   - **Unclear:** a promise from the signals with no owner and no date shows under Unclear. The person can pick "I owe it", "<name> owes it" or Dismiss.
     - Settled ones become ordinary open commitments.
     - Left alone, a promise is kept as an `UNCLEAR` commitment. It is never guessed, and it shows in Work → You owe → Unclear, where it can be settled or dismissed later.
   - **"N more found":** signals the four lists don't already cover, at 50% confidence or more, sit behind a collapsed "+ N more found". "Add" makes an item with evidence.
   - Signals the lists already cover (same paragraphs, or nearly the same words) are left out, so nothing is asked twice.
   - `WorkRepository.confirm` takes optional `WrapUpChoices`, so existing callers are unchanged.
5. **Transcript filter chips:** Decisions · Commitments · Questions · Risks, each with a count, driven by `segment_signals`. `SignalFilterHost` wraps the transcript. A recording with no signals shows the transcript exactly as before.

## Not built or changed

- **The decisions, commitments and questions in the Wrap-up still come from the existing four lists.** The signals of those kinds add evidence, the transcript chips, and change detection. They don't replace the lists, so old and new recordings behave alike. A signal of those kinds that the lists missed appears under "N more found".
- **`counterpartyPersonId` on items** is still never set. The signal's counterparty stays in the signal's `value`.
- **Notes on the Unclear rule.**
  - v34's rule (an unassigned action counts as yours, so it becomes your task) is unchanged for the four lists.
  - "Unclear" applies only to promises found through signals that no list already covers.
  - I did this so main users see no change. The orchestrator may want to revisit it.
- **The Wrap-up doesn't ask for a due date when settling an unclear promise.** Only who owes it is asked.

## How to see it

- **Wrap-up:** Work → a recording to review → Wrap-up. With signals present you'll see Changes, You owe, They owe, Unclear and "+ N more found".
- **Transcript chips:** open a work recording's Transcript tab. Chips appear only if it has signals.
- **Unclear promises:** Work → You owe → Unclear.

Nothing shows without a model, because signals come from the extraction. Everything already built keeps working.

## Risks / questions for the orchestrator

- **The prompts ask for a larger JSON object** for work recording types, which costs on-device output tokens (700). The signal field is optional, so a small model that skips it loses nothing. I haven't measured this on a device.
- **Change detection is lexical first**, so it will miss a rewording that shares few words. It's a proposal, and a miss costs nothing.
- **The change proposals' model check** uses `ModelCapability.SYNTHESIS`, like the pipeline's other intelligence calls.
- **Dismissals** ("Not the same", dismissed signals) are stored in shared preferences on the phone (`work_state`), not in the database. They aren't part of a backup.
